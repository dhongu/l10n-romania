Romania - Postal Codes

Modul pentru gestionarea codurilor poștale din România.

Funcționalități principale:

  • Adaugă modelul res.zip cu ~73.000 de înregistrări de coduri poștale românești, fiecare conținând: cod poștal, localitate, județ, tip stradă, nume stradă, sector (București), oficiu poștal.
  • Nomenclatorul este actualizat după posta-romana.ro (noiembrie 2026) pentru toate cele 42 de județe: străzile celor 54 de orașe cu coduri pe stradă și oficiul poștal al fiecărei localități. Străzile celor 269 de orașe mici la care Poșta are un singur cod vin din OpenStreetMap (ODbL), în modulul separat l10n_ro_zip_osm, care se instalează automat.
  • Datele sunt importate automat la instalare dintr-un fișier SQL. Fiecare cod e legat de județ după primele două cifre și, când modulul l10n_ro_city e instalat, de localitatea din nomenclatorul lui.
  • Extinde formularul partenerului (res.partner) cu câmpul Cod Poștal (zip_id), filtrat după localitate, care completează automat câmpul standard zip la selecție.
  • Căutarea codurilor poștale funcționează atât după codul numeric, cât și după numele străzii.
  • Suportă sectoarele municipiului București (1–6) cu legătură directă la localitățile corespunzătoare.

Usage

The postal codes are loaded on install; there is nothing to configure.

  1. Browse the postal codes. As an administrator, go to Contacts → Configuration → Localization → Zip Codes. The list shows one row per street in the big cities, with the street type, the street name, the postal code, the city, the state (county) and the country. The search bar looks up a postal code: type its first digits and press Enter.

  2. Open a postal code. A row shows everything the post office lists for it. In Bucharest the city is the sector, and the Sector field holds its number; Office and Address are the post office that serves the street.

  3. Find the street on a partner. On the partner form, pick the city from the list first (1); the state follows. Then type the street name in the postal code field right below the city (2), the one with the dropdown arrow; do not type in the grey ZIP field next to the state, which is filled in for you. Only the streets of the partner’s city are offered, each with its postal code, city and county in grey. The word order does not matter (Nicolae Balcescu finds Balcescu Nicolae), and you can also type the code or the street type (Strada Mircea). The post office data has no diacritics, so typing without them is safer. Left empty, the dropdown lists the first codes of the city, and Search more… the rest.

  4. Pick the street and save. The partner gets the postal code (3), the city (1), the state (2) and the country of the chosen row; the street and number of the address stay as you typed them. Invoices, delivery slips and e-Factura take the postal code from the partner’s address. If you change the city afterwards, or a module update changes the street’s code, pick the street again.

Changelog

19.0.0.0.19 (2026-11-02)

  • The streets of the small towns from OpenStreetMap (ODbL) move to the new module l10n_ro_zip_osm, installed automatically with this one. The streets already in a database stay; a new database gets them with the new module.

19.0.0.0.18 (2026-11-02)

  • The module no longer depends on l10n_ro_city: the county of each postal code comes from its first two digits, from a list in the module (Bucharest 01–06, Giurgiu 08), and the Bucharest codes are linked to their sector by its name. The codes are linked to the localities of l10n_ro_city when it is installed, as before, also when l10n_ro_city is installed in the same run or later: creating Romanian localities links the codes that have none. Without it they have the county only. The 19.0.0.0.17 migration becomes 19.0.0.0.18 and fills the county of the codes that had none, such as the Bucharest codes outside the sectors.
  • The postal code is indexed: applying the update on install or upgrade takes about 5 seconds instead of 19.

19.0.0.0.17 (2026-11-02)

  • More postal codes linked to their locality: the post office writes some names with a hyphen (Miercurea-Ciuc, Popești-Leordeni, Târgu-Jiu), others as “Village (Commune)” for the villages with the same name in a county, and the old list has “ª” for “Ș”. A row is linked only to a single locality, or to the single one with its postal code. On a new database, the rows without a locality go from 1,656 to 193.
  • Needs l10n_ro_city 19.0.1.10.2, which adds Breaza (Prahova), Băile Govora, Băile Olănești, Ocnele Mari and Eforie and fixes Sfântu Gheorghe and Popești-Leordeni. On update, the existing rows are linked again where they have no locality, and the Giurgiu rows get their county (prefix fixed in l10n_ro_city 19.0.1.10.1).

19.0.0.0.2

  • The postal code search now matches word by word, so the word order no longer matters. The nomenclature spells streets named after people surname first (Strada Balcescu Nicolae), while users type them the natural way round (“Nicolae Balcescu”) — and a plain substring match never bridged the two. The data is not even consistent with itself: 131 rows spell “Balcescu Nicolae” and none the reverse, while “Alexandru Ioan Cuza” appears both ways. Since these are largely the main streets of every city, a good part of the street data was unreachable in practice even with the search fixed in 19.0.0.0.1. A multi-word term is now split, and every word must match either street_name or street_type. Typing the street type along with the name (“Strada Mircea”) keeps working, and a single-word term behaves exactly as before.

19.0.0.0.1

  • Fix: searching a street name in the postal code field returned nothing. res.zip._search_display_name() only extended the search to street_name and street_type when the operator was different from ilike — but ilike is exactly the operator the autocomplete widget uses, so typing a street name in the “Postal Code” field on a partner produced zero results. Only a search by the postal code itself worked, since that is the model’s _rec_name. The street data was present all along (~52.000 rows, ~38.000 of them at street level), which made the symptom look like missing data: users on large cities (Bucharest, Constanța, Iași) reported “the streets are gone” and filled in the postal code by hand. The condition is now operator in ("ilike", "like", "="), and the operator received is reused in the extra leaves instead of a hardcoded ilike. This ports the fix already present on the 18.0 branch, which never reached 19.0. Note that on 19.0 only ilike/like actually reach this method: the ORM optimizes display_name = value into name in [value] on its own.
  • Add regression tests for the postal code search (street name, street type, name_search, and the postal code itself), previously only available on 18.0.
