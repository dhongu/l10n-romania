Overview

SPV Messages to Purchase Orders (Romania)

This addon extends the Romanian SPV message model (l10n.ro.message.spv) to link vendor bills received through e-Factura with Purchase Orders (PO), copy the SPV XML on the PO and link the bill lines to the PO lines, so the PO is not invoiced twice.

Key features

  • New fields on the SPV message:
    • Purchase Reference (purchase_ref) – extracted automatically from the XML at OrderReference/ID when available.
    • Purchase Order (purchase_order_id) – the linked PO, if any.
  • Two buttons on the SPV message form, shown only on purchase messages (vendor bills and vendor receipts):
    • Găsește Comanda (Find Order): searches purchase orders by reference (purchase_ref, or ref as fallback) in the vendor reference, source document or order number, restricted to the message partner and company and to orders that are not fully invoiced.
    • Creează Comanda (Create Order): performs the same search; if no order is found, creates a draft request for quotation for the message partner, with the reference as vendor reference, and links it.
  • When the reference only belongs to an order that is already fully invoiced, Find Order does not link it again; the error names the order and its bills.
  • A second click on a message already linked to the found order is blocked, so the document is not processed twice.
  • When a PO is found or created, a note is posted in the PO chatter with a copy of the SPV XML attached (ir.attachment on purchase.order, deduplicated by checksum or by name and mimetype). When the vendor bill does not exist yet, the XML is taken from the ZIP archive downloaded from ANAF.
  • The vendor bill created from the SPV message is linked to the PO lines (standard purchase matching), so the invoiced quantity is updated and the standard "Create Bill" does not produce a second bill. Bill lines that are not on the PO (transport, packaging) stay on the bill.
  • With Purchase UBL (deltatech_purchase_ubl) installed, the bill lines are imported on the PO: directly, with a notification, when every line is matched by vendor code or barcode and the totals match; otherwise the import wizard opens in preview, so the user decides for each line (use a product, create a new product or ignore it). The vendor bill option is off when the SPV bill already exists.
  • Non-blocking duplicate warnings in the chatter: a PO that already has another bill, "Create Bill" on a PO linked to an SPV bill, and a bill with the same deduplication key when the module providing that key is installed.

How it works

  1. Open an SPV message of type vendor bill.
  2. Check Purchase Reference (auto-filled from the XML if present) or Reference, and Partner.
  3. Use one of the header buttons:
    • Find Order: links the only match and continues with the import; if several orders match, opens the filtered list; if none, shows an error, naming the fully invoiced order when the reference belongs to one.
    • Create Order: searches first; if no order is found, creates a draft request for quotation for the message partner (the partner is required), links it and continues with the import; otherwise behaves like Find Order.

Configuration

No special configuration is required. Ensure users have access rights to Purchase Orders and attachments as per standard Odoo security rules. Installing deltatech_purchase_ubl is recommended, so the order lines are imported from the XML.

Compatibility

  • Odoo 19.0
  • Depends on: l10n_ro_message_spv, purchase
Versions

19.0.0.0.14 (2026-11-22)

Changed

  • Find Order on an SPV message now says when the reference belongs to a purchase order that is already fully invoiced, naming the order and its bills, instead of reporting that no order was found. Such an order is still not linked again (#9290).
  • Consultant sheet added (readme/FISA_CONSULTANT.md, with screenshots), and the module description rewritten from the code: the real button names, the fully invoiced orders left out of Find Order, the guard against a second click and the duplicate warnings.

19.0.0.0.13 (2026-11-16)

Changed

  • Apps Store page (static/description/index.html) regenerated with the Terrabit template.

19.0.0.0.12 (2026-10-22)

  • Listed on Odoo Apps as SPV Messages to Purchase Orders (was Purchase Message SPV). The technical name l10n_ro_message_spv_purchase does not change.

19.0.0.0.11 (2026-10-20)

  • Screenshots for the consultant sheet, generated by tests/test_screenshots.py: the notification of a clean invoice imported directly, and the import preview opened for an invoice with an unmatched line.
  • Test: the integration test with the real SPV invoice accepts both outcomes of "Create Purchase Order": the direct import, when the products carry the VAT of the Romanian chart of accounts and the total matches, or the preview otherwise.

19.0.0.0.10 (2026-10-20)

  • Changed: "Find Purchase Order" and "Create Purchase Order" no longer run the UBL import unattended when they attach the SPV XML to the order. When Purchase UBL (deltatech_purchase_ubl) is installed, they open its import wizard in preview instead, so the user decides for each invoice line: use a product, create a new product or ignore the line. Before, the lines that could not be matched were silently left out of the order. When every line is matched by vendor code or barcode and the order total matches the invoice, the invoice is imported without the wizard and only a notification is shown. The vendor bill option is off when the SPV bill already exists. Requires deltatech_purchase_ubl >= 19.0.1.4.14.

19.0.0.0.9 (2026-10-09)

  • Odoo Apps banner (static/description/main_screenshot.png), generated from banner.json.

19.0.0.0.8 (2026-09-30)

  • Own module icon in the flat style of the Terrabit modules, instead of the missing or generic one.

19.0.0.0.7 (2026-08-24)

  • Fix (regression from the fix in 19.0.0.0.4/0.0.5): once _post_spv_xml_on_purchase started reliably attaching the SPV XML on a purchase order created before the vendor bill exists, the headless UBL import in deltatech_purchase_ubl started running for that scenario too — and its product matching silently creates a new product when the invoice line has no supplier code and the name doesn't match an existing product exactly. _post_spv_xml_on_purchase now attaches the XML with purchase_ubl_no_new_products in context, so the automated import leaves an unmatched line (visible in the wizard's log) instead of creating a duplicate product. Requires deltatech_purchase_ubl >= 19.0.1.2.5.

19.0.0.0.6 (2026-08-20)

  • Fix: _purchase_search_domain_from_ref matched purchase orders by reference alone, so a generic/reused vendor reference (6 SPV bills over 6 months all reusing the reference "ZILNIC") kept linking new bills to the same, already fully-invoiced order. The domain now excludes orders with invoice_status == 'invoiced', so a reused reference on an order that still has open invoicing keeps matching (partial invoicing is unaffected), but once an order is fully invoiced a new bill with the same reference falls through to creating a new order instead of piling onto a closed one.

19.0.0.0.5 (2026-08-19)

  • Add an integration test using a real (anonymized) SPV invoice XML, wrapped in a ZIP as downloaded from ANAF: verifies the purchase order created before the bill ends up with its lines imported by deltatech_purchase_ubl, and cross-checks the imported total against the order total using the same _get_order_total_check control key that deltatech_purchase_ubl already runs (confirmed manually on a customer production order: order total 2749.37 RON matched the XML PayableAmount exactly).
